# Security Model

## Boundary sieciowa

W `docker-compose.yml`: API i Postgres są zbindowane do `127.0.0.1` (8000, 5432). MinIO ma porty `9000:9000` i `9001:9001` bez prefiksu `127.0.0.1:` — nasłuch na wszystkich interfejsach.

For a long-lived portal/API service, keep uvicorn bound to `127.0.0.1` and expose UI routes only through a trusted reverse proxy, VPN or local network boundary. The repo includes examples:

- `ops/systemd/log-platform-api.service.example` — localhost-bound API/portal service.
- `ops/nginx/log-platform.conf.example` — simple nginx proxy to `http://127.0.0.1:8000` preserving `Host`, `X-Forwarded-For` and `X-Forwarded-Proto`.

HTTPS termination is host-managed and not implemented by the FastAPI app. Do not publish the bearer-token JSON API or portal session cookie over plaintext HTTP beyond localhost.

## Autoryzacja API (wewnętrzna platforma)

Bearer token:

- read -> `API_READ_TOKEN`
- write -> `API_WRITE_TOKEN`

To **jeden poziom** kontroli dostępu do API platformy (runy, logi, artefakty, prune). Nie zastępuje on uwierzytelniania u dostawców zewnętrznych w **Workflow A**.

Artifact upload idempotency uses this same machine-level `API_WRITE_TOKEN` boundary. `(idempotency_scope, idempotency_key)` is globally unique inside the platform database, not per tenant or portal user. Keys are opaque correlation values, not secrets: never include customer data, filenames, email addresses, credentials, report values, or content. The API logs only scope plus a shortened identity digest. Authorization is checked before keyed lookup, so unauthenticated callers cannot use replay behavior to discover artifact IDs.

Workflow B Stage 1 raw/normalized keys follow this rule: they hash only a fixed role/version contract, opaque `raw_file_id`, and source SHA-256. Reconciliation results expose only safe IDs, role, outcome, version and shortened digest; they do not expose mailbox fields, filenames or report content.

Endpointy manualnych adnotacji artefaktów JSON (`PATCH /artifact-browser/artifacts/{artifact_id}/metadata`, `POST/DELETE /artifact-browser/artifacts/{artifact_id}/tags...`) używają tego samego `API_WRITE_TOKEN`. Tokenowe `/artifact-browser/*` pozostaje machine-level access i nie stosuje per-user RBAC w Phase 6.

## Artifact Explorer UI — lokalni użytkownicy i RBAC

Server-rendered UI pod `/artifact-explorer` używa lokalnego logowania na użytkowników z Postgresa:

- `artifact_users` — `username`, hash hasła PBKDF2-HMAC-SHA256, `is_active`, `is_admin`,
- `artifact_roles`,
- `artifact_user_roles`,
- `artifact_role_permissions`.

Hasła nie są przechowywane jawnie. Hash format: `pbkdf2_sha256$iterations$salt$digest`, z per-user salt.

Sesje UI są podpisanym cookie `artifact_explorer_session`, ważnym domyślnie 12 godzin. Produkcyjnie ustaw:

```text
ARTIFACT_EXPLORER_SESSION_SECRET=<long random secret>
```

Jeśli ta zmienna nie jest ustawiona, proces API używa losowego sekretu development-only; logowanie działa, ale wszystkie sesje wygasają po restarcie procesu.

Uprawnienia są allow-only. `NULL` w kolumnie filtra permission oznacza wildcard; wartość nie-NULL musi dokładnie pasować do metadanych artefaktu. Obsługiwane filtry permission: `workflow_name`, `stage_name`, `artifact_role`, `report_type`, `client_code`, `file_ext`, `layout_version`, `tag`. Akcje:

- `can_view` — lista/detail,
- `can_preview` — sekcja preview w UI,
- `can_download` — download/inline download z UI,
- `can_edit_annotations` — opis, manual metadata JSON i tagi w UI.

Admin (`artifact_users.is_admin=true`) omija artifact-level checks. Deny rules nie są zaimplementowane.

Virtual folder pages are visible to logged-in UI users for navigation, but artifact rows inside folders still pass through the same artifact-level RBAC (including smart folders, where matches are computed from `search_query_json`). Folder management in the UI is admin-only: create, rename, delete, manual artifact memberships, and smart criteria edits. There are no per-folder permissions; smart folders do not grant extra access beyond artifact RBAC.

Manualne adnotacje i folder writes zapisane przez UI używają audit actor `artifact_explorer:<username>`; tokenowe API nadal używa `api_write_token`.

## User Portal i Admin Portal (Phase 1 / 2A / 2B / 2C / 3A / 3B / 3C / 4A / 4B)

Server-rendered portale pod `/user` i `/admin` uzywaja tego samego lokalnego session-cookie auth co Artifact Explorer, ale sa osobnymi powierzchniami UI:

- `/user/*` wymaga zalogowanego aktywnego uzytkownika i pokazuje User Portal. Po Phase 4B effective portal access laczy direct user assignments i aktywne group assignments przez OR semantics. `/user/database` pokazuje dataset cards tylko wtedy, gdy aktywny klient ma effective `can_view_database=true`, dataset jest aktywny i user ma direct albo active-group dataset assignment z effective `can_view_rows=true`. `/user/database/datasets/{dataset_id}` wykonuje read-only row browsing dla tych datasetow, wybierajac tylko katalogowo widoczne kolumny. `/user/database/datasets/{dataset_id}/export` uzywa tego samego safe query modelu i wymaga dodatkowo effective `can_export_rows=true`. Unified `POST /user/database/datasets/{dataset_id}/exports` nie zapisuje direct exports <=20,000 rows jako artefaktow; dla async exports kolejkuje tylko zwalidowany snapshot i, po migracji 044, tworzy wlascicielowi systemowy folder `Database Exports`. `/user/reports` pokazuje aktywne report folders przypisane temu userowi bezposrednio albo przez aktywna grupe, ale tylko jesli user ma effective `can_view_reports=true` dla klienta folderu; dodatkowo pokazuje owner-scoped system folder Database Exports, gdy istnieje.
- `/admin/*` wymaga `artifact_users.is_admin=true`. Uzytkownik bez admina dostaje strone 403, a nie dostep do ekranow admina.
- `/admin/users*` w Phase 2A graficznie zarzadza lokalnymi UI users z `artifact_users`: tworzenie kont, aktywacja/dezaktywacja, admin access, reset hasla i przypisania istniejacych `artifact_roles` przez `artifact_user_roles`. Hasla sa hashowane tym samym PBKDF2 helperem co istniejace logowanie; plaintext nie jest zapisywany.
- `/admin/client-access*` w Phase 2B graficznie zarzadza `portal_clients` i przypisaniami `portal_user_clients`. Te tabele sa portal-level foundation dla przyszlych Reports Explorer i Client Database Explorer, a nie Artifact Explorer RBAC. Nie zawieraja connection stringow, hasel ani sekretow.
- `portal_user_clients` przechowuje flagi `can_view_database`, `can_view_reports` i `can_export_database`. `can_view_reports` jest wymagane dla report-folder visibility i dla kazdego portal preview/download. Flagi nie grantuja dostepu do `/artifact-explorer/*`, nie zastepuja `artifact_roles` / `artifact_role_permissions`, i nie grantuja SQL access.
- `/admin/groups*` w Phase 4B zarzadza `portal_groups`, `portal_group_users` i `portal_group_clients`. Portal groups sa osobne od `artifact_roles`: nie grantuja technicznego Artifact Explorer RBAC, nie zmieniaja `artifact_user_roles`, nie zawieraja sekretow i nie tworza implicit access do wszystkich klientow. Nieaktywne grupy nie uczestnicza w effective access.
- `/admin/report-folders*` zarzadza `portal_report_folders`, `portal_report_folder_users` i `portal_report_folder_groups`. Folder zapisuje allowlistowany `search_query_json`; `client_code` pochodzi z folderu, nie z JSON. Group-folder assignment jest dozwolony tylko wtedy, gdy grupa ma `portal_group_clients.can_view_reports=true` dla klienta folderu. Dla user-facing report artifact access musza byc spelnione jednoczesnie: aktywny user, aktywny folder, aktywny klient, direct albo active-group folder assignment, effective `can_view_reports=true`, dopasowanie artefaktu do filtrow folderu i rowny `artifact.client_code`. Artefakty bez `client_code` nie sa eksponowane przez portal report folders w tej fazie.
- `/admin/client-access/database*` zarzadza `portal_database_datasets`, `portal_database_dataset_columns`, `portal_database_dataset_users` i `portal_database_dataset_groups`. To portal-level allowlista datasetow i kolumn, nie regular-user przegladarka schematow. `schema_name`, `table_name`, `column_name` i `default_date_column` sa walidowane jako pojedyncze bezpieczne identyfikatory; UI nie przyjmuje SQL fragments, arbitralnych kolumn, funkcji, operatorow, komentarzy ani JSON path expressions. Multi-database model: control-plane `logdb` (gdzie zyja `runs`/`logs`/`artifacts` oraz tabele portalu) jest osobne od per-client business databases. `portal_clients.database_name` mapuje portal client na jego business database i jest **wylacznie nazwa bazy PostgreSQL** (allowlista `^[A-Za-z_][A-Za-z0-9_]{0,62}$`), nigdy DSN ani credentials. Admin-only metadata discovery oraz user-facing row browsing/export lacza sie z **zmapowana client database**, a nie z `logdb`: connection helper bierze host/port/user/password z platform Postgres env i podmienia tylko nazwe bazy, w read-only session. Jesli klient nie ma `database_name`, dataset create page pokazuje konkretny komunikat ("This client does not have a database name configured...") zamiast generycznego metadata error. Admin-only guided selectors odpytuja tylko `information_schema.schemata`, `information_schema.tables` i `information_schema.columns`, wykluczaja system schemas (`pg_catalog`, `information_schema`, `pg_toast`) i przekazuja schema/table jako bind params tam, gdzie sa filtrem; nie pokazuja wartosci rows, sekretow, DSN, tokenow, storage keys ani raw SQL. Regular users nie maja schema/table/column discovery. Dataset deactivation ustawia tylko `portal_database_datasets.is_active=false`; nie usuwa ani nie modyfikuje fizycznej tabeli, danych klienta, assignments ani audit history. Direct dataset assignment wymaga effective `can_view_database=true` dla klienta datasetu; group dataset assignment wymaga `portal_group_clients.can_view_database=true` dla klienta datasetu. Dataset flags `can_view_rows`, `can_filter_rows` i `can_export_rows` lacza direct i group grants przez OR semantics. Assignments nie nadaja dostepu do Artifact Explorer. Query engine ponownie waliduje stored identifiers, cytuje allowlistowane identyfikatory, parametryzuje wszystkie wartosci filtrow, wymusza `limit <= 500`, wybiera tylko `is_visible=true`, sortuje tylko po `is_sortable=true` i filtruje tylko po `is_filterable=true` gdy effective assignment ma `can_filter_rows=true`. Export reuseuje ten sam query path, eksportuje tylko visible columns, obsluguje CSV i XLSX, wymusza fixed direct cap `20000`, kieruje explicit background requests przez job queue dla `20001`-`1000000` rows, oraz nie streamuje nieograniczonych wynikow.
- Last-active-admin protection blokuje odebranie admin access albo dezaktywacje ostatniego aktywnego admina. Hard delete kont nie jest zaimplementowany.
- `/artifact-explorer/*` pozostaje technicznym narzedziem operatorskim dla artefaktow, preview, download, metadata, tagow, virtual/smart folders i artifact-level RBAC.

Kanoniczna trasa logowania UI to `/login` (oraz `/logout`); `/artifact-explorer/login` i `/artifact-explorer/logout` pozostaja aliasami zgodnosci o identycznym zachowaniu. Wszystkie korzystaja z jednego, platformowego cookie sesji (`artifact_explorer_session`, path `/`, podpisane HMAC, 12h). Token API (`/artifact-browser/*`, `/runs`, `/logs`, `/artifacts*`, `/maintenance/prune`) uzywa Bearer tokenow i pozostaje oddzielone od sesji UI. Model kont jest tymczasowo wspoldzielony z `artifact_users`, aby zachowac istniejace logowanie. Report-folder permissions sa portal-specific i nie sa technicznymi Artifact Explorer roles. Phase 3C zapisuje `portal_audit_events` dla database export attempts: success, denied, validation_failed i failed. Phase 4A rozszerza audit na loginy/logouty, denied portal/admin/report/database access, admin user-management, client access, report-folder changes, report preview/download, database catalog changes i database row browsing. Phase 4B dodaje audit events dla portal group create/update, membership, group client access oraz report-folder/database-dataset group assignments. Audit metadata przechodzi przez sanitizer, ktory redaguje klucze wygladajace jak `password`, `password_hash`, `token`, `api_key`, `secret`, `authorization`, `cookie`, `session`, `connection_string`, `dsn`, `sql`, `query_sql`, `raw_sql` i `minio`. Metadata moze zawierac bezpieczne summary (changed fields, target ids, format, limity, row count, filter keys, sort/date range), ale nie powinna zawierac raw SQL, connection strings, sekretow, plaintext passwords, tokenow ani wartosci rows. Audit insert failures sa non-blocking i trafiaja do server logs. Docelowe application users, immutable SIEM-grade audit storage i global search pozostaja planowane. Nie ma self-registration, email password reset, fizycznych zmian schematu klienta ani write operations.

Operational hardening notes:

- Use HTTPS or a trusted reverse proxy/VPN boundary before exposing any UI route beyond localhost. The repo does not provide TLS termination.
- Keep the API service bound to `127.0.0.1` when reverse proxying; treat any `0.0.0.0` bind as container-internal or development-only unless another network control layer is in place.
- Set a stable `ARTIFACT_EXPLORER_SESSION_SECRET`; without it, UI sessions are invalidated on API restart and are not deployment-ready. The same secret also derives Database Explorer opaque row references (`docs/29`), so an unset or changed value additionally invalidates every copied `row=` URL. The production Compose API service requires it (`${ARTIFACT_EXPLORER_SESSION_SECRET:?required}`) and refuses to start without it; the value is supplied by the deployment environment and is never committed.
- Bootstrap the first admin with `scripts/bootstrap_portal_admin.py` or the legacy `scripts/create_artifact_admin.py`; prefer `--password-env` and do not place plaintext passwords in shell history, logs, `.env`, or docs.
- Local UI users are separate from the bearer-token Artifact Browser API. Portal groups are separate from technical Artifact Explorer `artifact_roles`.
- Client/report/dataset/group assignments are explicit and additive. They do not grant arbitrary SQL, do not grant client DB writes, and do not grant technical Artifact Explorer RBAC.
- Database exports are audited and use the allowlisted row-browser query path. Async Database Exports folder routes are owner-scoped: they resolve only the signed-in user's `database_export_system_folders` row and the user's own jobs; non-owners are denied before artifact streaming. Failed jobs show only the generic safe portal message, pending rows have no download action, and expired/deleted artifacts have no stale download link. Audit metadata intentionally avoids passwords, tokens, raw SQL, connection strings, storage keys, object identifiers, internal exception text, and row values. Existing technical Artifact Explorer admin behavior is unchanged, with common expiry checks still blocking expired downloads.

## Sekrety

Repo nie powinno zawierać plików z sekretami (`.env`, tokeny, hasła).
Faktyczne pliki env są utrzymywane na hoście.

### Tracked env backups — removed 2026-08-19, history still exposed

Four credential-bearing `.env.bak.*` files had been committed and reached `origin/main`. They are
removed from the current tree, moved out of the working tree, and blocked from returning by the
`.gitignore` backup patterns plus `ops/tests_manual/test_tracked_secret_backup_hygiene.py` (a
filename/pattern guard — it never reads or prints a value).

**Removal from the tree is not remediation of the exposure.** No history rewrite was authorized or
performed, so every value stays reachable in Git history on the remote. The only real remedy is
rotation, and rotation is still outstanding:

- `POSTGRES_PASSWORD`, `MINIO_ROOT_PASSWORD`, `API_READ_TOKEN`, `API_WRITE_TOKEN` — already
  superseded in live configuration, but their historical values are consumed by long-running
  processes that load them once (module-level constants in `api/main.py`; Compose interpolation at
  container creation). They cannot be rotated without a restart/recreation.
- `AUTOMATION_SMTP_PASSWORD`, `ECO_WEEKLY_EMAIL_SMTP_PASSWORD` and the ten per-client Telematics
  credentials `{BIED12,ALPHA,FOXTROT,DELTA,ECHO}_{API_KEY,DB_KEY}` — still live. Their consumers are
  one-shot timer jobs that re-read configuration per invocation, so the *consumer* side needs no
  restart, but the authoritative store (`/etc/log-platform/runtime.env`, root-owned `0600`,
  precedence over the repository `.env`) is not writable by the platform account, and the providers
  are external (Telematics, client-owned business databases, external mail host) with no documented
  rotation mechanism in `ops/`.

Treat these as compromised-pending-rotation. See `docs/17` §5.6 for the rotation batch this belongs
to.

Hasła kont SMTP dla powiadomień Stage 2 (`AUTOMATION_SMTP_PASSWORD`), Eco Driving weekly (`ECO_WEEKLY_EMAIL_SMTP_PASSWORD`) oraz BRAVO00016 weekly (`BRAVO_ECO_WEEKLY_EMAIL_SMTP_PASSWORD`, `BRAVO_ECO_WEEKLY_EMAIL_IMAP_PASSWORD`) są sekretami hostowego środowiska tak samo jak tokeny API i hasła DB. Kod wysyłki używa wyłącznie dedykowanych zmiennych `AUTOMATION_SMTP_*`, `ECO_WEEKLY_EMAIL_*`, `ECO_PERSON_EMAIL_*` albo `BRAVO_ECO_WEEKLY_EMAIL_*`; logi błędów nie powinny zawierać wartości hasła ani pełnej konfiguracji SMTP/IMAP.

BRAVO00016 Sent-folder archiving (weekly and monthly) stores exact MIME bytes in the client business database after SMTP success so archive-only recovery can append the same message without SMTP resend. Treat `eco_person_{weekly,monthly}_email_send_log.sent_mime_bytes` as protected operational content: it may contain recipient addresses and rendered email bodies, and should not be exported to tickets, docs, logs, or unprotected reports. `BRAVO_ECO_WEEKLY_EMAIL_REPLY_TO=` means omit the `Reply-To` header, not emit an empty header.

The BRAVO00016 Eco Person CSV and `eco_person_people` rows contain personal names and email addresses. Keep source/import files outside Git, validate them locally, and mask recipient addresses in reports. Email idempotency is logically scoped by the physical `person_name_group_key`, but the serialized idempotency key stores only its SHA-256 digest; it must not expose the physical name or email. Send-log identity columns remain protected client-business data.

### `suspected_bug` payload sanitization

Incydenty `suspected_bug` (`suspected_bug_incidents`, `suspected_bug_occurrences`, `suspected_bug_email_outbox`, `logs.context`) opisują defekty i naruszone inwarianty, więc payload jest sanityzowany w `api/suspected_bug.py` **przed** zapisem, a nie dopiero przy renderowaniu maila:

- allow-lista pól kontraktu `SuspectedBugEvent`; nieznane pola są odrzucane przy wejściu;
- klucze wyglądające na sekret (`pass*`, `secret`, `token`, `credential`, `authorization`, `api_key`, `access_key`, `private_key`, `dsn`, `connection_string`, `smtp*`, `imap*`, `cookie`, `session_id`) zapisują `[redacted]` zamiast wartości;
- wartości: credentials w URI (`scheme://user:pass@host`), bloki `-----BEGIN … PRIVATE KEY-----` oraz wzorce `password=…` / `api_key: …` w wolnym tekście i w stack trace są redagowane;
- adresy e-mail są maskowane do `p***@domena` wszędzie, gdzie nie są niezbędne; pełna lista odbiorców istnieje wyłącznie w `suspected_bug_email_outbox.recipients`, a `ops/inspect_suspected_bugs.py` domyślnie ją maskuje (`--show-recipients` wymaga świadomej decyzji);
- twarde limity: 500 znaków na string (2000 dla `summary`/`suggested_action`), 25 elementów listy, 40 kluczy mapy, głębokość 4, ostatnie 40 linii i 4000 znaków stack trace; każde przycięcie ustawia `truncated=true`;
- brak zrzutów środowiska, całych plików źródłowych, nieograniczonych wierszy DB i lokalnych zmiennych wyjątku; identyfikatory rekordów są tylko ograniczonym dowodem (np. 20 przykładowych `provider_trip_id`);
- HTML maila jest escapowany (`html.escape`) dla wszystkich wartości payloadu.

Tabele incydentów i outboxu nie przechowują żadnych sekretów SMTP: `recipient_config_ref` trzyma tylko nazwę zmiennej konfiguracyjnej (np. `SUSPECTED_BUG_ALERT_TO`), a transport używa istniejących `AUTOMATION_SMTP_*` rozwiązywanych w procesie workera. Brak skonfigurowanych odbiorców oznacza zapis logu i incydentu bez wysyłki — nigdy fallback na odbiorców raportowych lub klienckich. Odbiorcy alertów są adresami operacyjnymi zespołu, nie danymi klienta; ich lista nie powinna trafiać do ticketów ani dokumentacji.

Workflow A control-plane nie przechowuje wartości haseł API ani haseł baz klientów. Kolumny `provider_basic_auth_password_secret_ref` i `client_db_password_secret_ref` przechowują referencje:

- nazwa env-var, np. `DELTA_API_KEY`,
- albo `file:/abs/path/to/secret.txt`.

Resolver `jobs/api/telematics/secret_resolver.py` odczytuje sekret dopiero w procesie joba. Brakująca lub pusta referencja kończy run błędem; wartości sekretów nie powinny trafiać do `runs.params`, logów ani YAML onboardingu.

Workflow B Stage 2 używa tych samych `client_db_password_secret_ref` tylko wtedy, gdy dla typu raportu skonfigurowano `workflow_b_control.report_type_registry.id_sync_column_name`. Służy to do odczytowego sprawdzenia `client_trips.registration`, `client_trips.chassis_number` i `client_trips.driver_name` we włączonych bazach klientów w celu wykrycia `client_code`. Stage 2 nie loguje wartości sekretów ani pełnych DSN; logi diagnostyczne powinny ograniczać się do `report_type`, `raw_file_id`, nazwy kolumny, liczby kandydatów i dopasowanych `client_code`.

Idempotency key cleaned outputu Stage 2 jest nieodwracalnym SHA-256 z versioned constants, `raw_file_id` i źródłowego SHA-256. Scope/key i skrócony digest są non-secret correlation data; nie wolno dodawać do nich `client_code`, nazw plików, ścieżek, danych raportu ani danych email.

Workflow B Stage 3 używa `client_db_password_secret_ref` do zapisu finalized cleaned reports do bazy klienta wykrytej po `client_code`. Logi Stage 3 nie powinny zawierać haseł, pełnych DSN ani wartości sekretów; diagnostyka ogranicza się do `raw_file_id`, `client_code`, `report_type`, identyfikatora artefaktu źródłowego, tabeli docelowej i liczników insert/update/skip. Nazwa tabeli docelowej pochodzi z kanonicznego `stage2_report_type` i jest walidowana jako bezpieczny identyfikator SQL. Nazwy kolumn raportu są zachowywane, ale cytowane jako identyfikatory; puste nazwy, NUL byte i kolizje z technicznymi kolumnami `_loaded_at`, `_raw_file_id`, `_source_artifact_id`, `_source_filename`, `_stage3_run_id` kończą load błędem zamiast cichego nadpisania.

Stage 3 nie wykonuje importu jako `POSTGRES_USER` i nie używa admin credentials w recurring runtime. `auto_grant_permissions=true` jest odrzucane. Adminowe `POSTGRES_USER` / `POSTGRES_PASSWORD` mogą być użyte wyłącznie przez kontrolowaną migrację `db/client_business/042_workflow_b_stage3_runtime_schema.sql` oraz pozajobowy `ops/grant_workflow_b_stage3_permissions.py --apply`. Runtime role nie dostaje ownership, `SUPERUSER`, `CREATEDB`, `CREATEROLE`, database/schema `CREATE` ani default privileges; wymagane są tylko `CONNECT`, schema `USAGE`, DML na właściwych, zarejestrowanych tabelach `telematics_reports` oraz `SELECT, UPDATE` na `public.client_trips` dla Report 207.

## Workflow A — docelowe wymagania (per klient)

Dla głównego kierunku strategicznego zakłada się, że **każde konto klienta** może mieć:

- inne poświadczenia do API zewnętrznego,
- inne (lub dodatkowe) ustawienia połączenia (baza URL, timeouty, limity).

**Zalecenie operacyjne**: izolować konfigurację i sekrety per klient (osobne pliki `EnvironmentFile`, osobne unit systemd, lub `file:` references), aby uniknąć przypadkowego współdzielenia jednego kontekstu sekretów. Wewnętrzne API platformy nadal ma tylko wspólne tokeny read/write; izolacja per klient dotyczy jobów i hostowego środowiska, nie wielotenantowego auth API.

## Eco Driving Explorer — read API RBAC, isolation, audit (Stage 2)

Read-only JSON API pod `/user/eco-driving/api/*` (patrz `docs/03_api_spec.md`) reuses the existing portal session cookie `artifact_explorer_session` and the current authenticated-user lookup — no new cookie, no Bearer auth for these user endpoints, no second user table, no parallel auth system. Unauthenticated requests get a JSON `401`; authenticated-but-unauthorized get `403`; the API never discloses whether another client/provider exists.

**Dedicated RBAC (migration `051_portal_eco_driving_permissions.sql`).** Additive, idempotent (`ADD COLUMN IF NOT EXISTS`), forward-only. It adds three `BOOLEAN NOT NULL DEFAULT FALSE` columns to **both** `portal_user_clients` and `portal_group_clients`:

- `can_view_eco_ranking` — list providers/periods/ranking entries and open the persisted ranking-entry summary. No trip-level records.
- `can_view_eco_trip_details` — list contributing trips, view safe technical trip scoring inputs, and run reconciliation. Requires `can_view_eco_ranking`.
- `can_view_eco_trip_routes` — reserved for a later stage (location/address/map fields). Grants **no** additional data now; added early so the RBAC contract is stable before route data lands.

The migration performs **no backfill** from `can_view_database`/`can_view_reports`, **no automatic grants**, and **no automatic enablement** for existing users/groups; existing rows receive `FALSE` and existing Database Explorer/Reports permissions are unchanged. Rollback is via a new forward migration dropping the three columns on both tables (the file itself is never edited once applied). No Eco export permission is added in this stage.

**Effective access** mirrors the existing additive portal model: for a client, each capability is the union `direct OR any active-group` flag (`bool_or` over `portal_user_clients`, and over `portal_group_clients` joined through active `portal_groups`/`portal_group_users`). A missing direct row and no matching active-group row means no access; one `FALSE` source never overrides another source's `TRUE`. The result is a typed `EcoDrivingClientAccess` whose optional `sources` field records only `direct`/`group` (never internal IDs). **Administrators do not bypass client grants** — this preserves the existing portal convention where `artifact_users.is_admin` only unlocks the `/admin` surface and still requires direct/group grants for client data.

**Client/provider isolation.** The browser supplies only `client_code`, `ranking_family`, and filter/pagination params. It never supplies platform `client_id`, database name/host, schema, table, provider class, arbitrary provider key, or SQL. The server resolves `client_code` → active `portal_clients` → enabled `workflow_a_control.client_account` (trusted UUID `client_id` + `client_db_name`) → registered provider factory, cross-checks the portal database mapping against the control-plane config, and **fails closed** on mismatch (`ENVIRONMENT_CLIENT_MISMATCH` → HTTP 503). The `client_id` passed to the provider always comes from trusted platform configuration; every client-business query is read-only, statement-timeout bounded, and scoped by that trusted `client_id`, so a permission or period token or `assigned_id` from one client can never reach another client's data. Provider availability is driven by an explicit registry allowlist, never by the mere existence of database tables.

**Data exposure.** Trip responses expose only safe scoring-explainability fields (no latitude/longitude, no start/end address, no email, no raw driver name, no route polyline, no unrestricted `client_trips` payload); private and non-aggregated trips are excluded and the period end is exclusive. Persisted scoring `Decimal` values are serialized as decimal strings. Reconstructed lineage is always `RECONSTRUCTED_CURRENT_STATE`; `MATCH` is not immutable historical proof and `EXACT_SNAPSHOT` is not available.

**Audit.** Reuses `portal_audit_events` and the existing sanitizer. Successful access emits one sanitized event per request (`eco_driving_providers_viewed`, `eco_driving_periods_viewed`, `eco_driving_ranking_viewed`, `eco_driving_ranking_entry_viewed`, `eco_driving_trip_details_viewed`, `eco_driving_reconciliation_viewed`). Metadata is limited to safe values; the raw `assigned_id` is never stored — only a deterministic non-reversible short SHA-256 `assigned_id_digest`. No driver name, email, address, coordinates, SQL, or cookie/session data is logged, and failed authorization is not audited with request values.

## Docker API execution trust boundary

The privileged surface of this platform follows one rule: **root-driven operations never execute code from the user-writable checkout.** The environment-identity helper already enforces it by importing its parser only from root-owned `/usr/local/lib/log-platform/environment_identity_file.py`. The Docker API was the exception, and this section records how that is closed.

**The defect.** The `api` service bind-mounted `/opt/log-platform/api` to `/app` read-write and ran as container UID 0 on a rootful daemon with no user-namespace remapping, the full default capability set (`CAP_DAC_OVERRIDE`, `CAP_CHOWN`, `CAP_SETUID`, …) and `NoNewPrivs=0`. A privileged recreation of that container therefore executed operator-mutable source with host-root filesystem authority, and the image digest attested nothing: the image's baked `/app` was a stale partial snapshot shadowed by the bind for months.

**The repository remediation.** The base `docker-compose.yml` is the only production definition. Its `api` service has no application-source bind, names its image explicitly (`log-platform-api:latest`), and runs `user: "1000:1000"` with `cap_drop: [ALL]` and `security_opt: [no-new-privileges:true]`. `api/Dockerfile` bakes the build context into `/app` as root-owned, non-writable, mode-normalized files — normalization is required because `COPY` preserves build-context modes and four `eco_driving_explorer/admin_*.py` modules are `0600` in the checkout, which a non-root runtime user could not import. `api/.dockerignore` keeps bytecode caches, virtualenvs, editor state and any `.env*` out of the image. The live source bind survives only in `docker-compose.dev.yml`, which Compose never auto-loads.

Consequences: production API code is selected by the image rather than the checkout; the image digest becomes meaningful evidence of executed code, which is what the promotion contract's Docker image binding always assumed; and the container can no longer author host files as root, nor regain privilege through a setuid path.

**Runtime identity 1000:1000** is the existing `logplatform` service account — the same identity the native systemd API runs as — so both API deployments share one identity and the development bind stays readable without relaxing host modes.

**Accepted trust-model decision (Task Contract Amendment).** `logplatform` remains a **trusted privileged operator** and keeps its `docker` group membership. That membership is a host-root-equivalent primitive in its own right, independent of any container configuration. Reducing it — a narrow Docker sudo broker, rootless mode or daemon-wide `userns-remap` — is a deliberate, separately scoped future hardening item and is **not** a prerequisite for the pending credential-rotation work. This is a recorded decision, not an oversight. What the remediation above does establish is narrower and sufficient for that gate: privileged deployment operations no longer execute mutable checkout code as container root.

**Deployment status — deployed and verified in production on 2026-08-09.** Candidate verification completed first; production then recreated **only** the Docker API service, leaving PostgreSQL, MinIO and the native `log-platform-api.service` operationally unchanged. The live container was verified running from the image with no application-source bind and no host mount at all, as UID/GID `1000:1000`, with every Linux capability set zero, `NoNewPrivs=1`, `Privileged=false`, published on `127.0.0.1:8000`, health and authenticated reads passing and a zero-entry `docker diff`.

The runtime attestation is the immutable image ID, `sha256:c718529f89ad2a822f5f014de6f8cdafa6db2f5227637c8fa4176757f7a6df46` — not the `log-platform-api:latest` tag, which is a mutable pointer and proves nothing on its own. Check the ID on the running container.

Rollback material is deliberately retained until the operator accepts the deployment, and consists of **both** the previous immutable image and the previous bind-based deployment definition; the image alone is not a valid rollback, because its baked `/app` is a stale snapshot. `ops/tests_manual/test_docker_api_execution_boundary.py` guards the configuration against regression; it asserts nothing about the running container, so runtime claims must be re-established by inspecting it. Full deployment record: `docs/17_production_hardening_roadmap.md` § 5.6.

## Environment promotion security boundary

Environment promotion is an identity-classification operation, not database provisioning. The operator must supply the existing platform UUID and an existing UUID for every explicitly selected client. The CLI resolves client IDs, database names, users, and expected identities from `workflow_a_control.client_account`, then independently checks the locked marker row in each connected database. Every write predicate contains the expected UUID, but every `UPDATE` sets only an environment column. UUID fields, client IDs/codes, database names, business tables, schedules, and secrets are outside the write set.

Execute requires all of the following: canonical case-sensitive source/target values, distinct profiles, exact selected scope, UUID equality at every surface, verified backup/checkpoint evidence, a production-readiness pass, the promotion advisory lock, migration 053, and an exact attestation generated from the canonical immutable plan hash. The journal stores only the SHA-256 of the attestation. A changed client list, UUID, runtime path/checksum, backup reference, step order, or environment produces a different plan and cannot resume an existing journal.

New forward approvals use `promotion_plan_contract_version=5` and `contract=v5` only. The compact, sorted canonical JSON contains the effective helper-specific sudo contract (absolute path, one matching rule, normalized rule, `NOPASSWD`, run-as `root`, no later conflict, collection method and the normalized `sudo -n -l` fingerprint), rather than trusting an adjacent report. It also contains a sorted repository-relative map of every security-critical planner/serializer/validator/mutation/journal/helper/resume/recovery module and its regular-file, non-symlink SHA-256 binding. Any sudo-policy or source-byte change invalidates approval before journal creation.

The v5 plan cryptographically binds every rolled-back historical journal row to its original v4 plan hash and checksum-bound rollback evidence path, hash, schema and safe metadata. Durable current marker/journal state is authoritative; historical `completed_steps` is retained only as non-authoritative evidence. Rolled-back rows do not block a new promotion, but deletion, regression, replacement or evidence drift changes or blocks the plan. The sorted `excluded_actions` list names worker/email/SMTP/IMAP activation, ALPHA backfill, snapshot/schedule/business/schema work, initial runtime restart/recreation, timer/prune/backup/daemon actions, recovery cleanup/removal, UUID generation/change, direct marker update, and automatic retry/resume/rollback individually.

Immediately before the first write, execute reconstructs and compares the exact full v5 canonical bytes. Bounded drift classes are `PROMOTION_PLAN_CONTRACT_SUPERSEDED`, `SUDO_POLICY_DRIFT`, `PROMOTION_IMPLEMENTATION_ASSET_DRIFT`, `PROMOTION_HISTORY_DRIFT`, `PROMOTION_EXCLUSION_CONTRACT_DRIFT`, category-specific existing v4 drift codes, and the final `PROMOTION_IMMUTABLE_BINDING_DRIFT`. No journal row exists before this comparison succeeds. v3/v4 forward attestations are superseded; v4 remains valid only as historical evidence and as the original input to recovery-v2.

Runtime identity is separated from secrets. `/etc/log-platform/environment-identity.env` contains exactly the one non-secret canonical assignment and is `root:logplatform` mode `0640`; repository `.env`, host/API/runtime/backup env files must not define the key after provisioning. The parser performs no shell evaluation, interpolation or quote handling. It rejects unknown/duplicate keys, unsupported case-sensitive values, malformed UTF-8, symlinks and wrong owner/group/mode. Readiness hashes repository and installed consumer configuration and separately proves semantic identity, configured canonical-source provenance, and process/container provenance. Semantic equality alone never proves convergence: systemd must expose the canonical source after every `EnvironmentFile=` reset and the healthy service invocation must postdate that effective configuration; Compose must resolve the canonical source and the healthy API container must postdate it. Missing or unknown provenance is `RUNTIME_RELOAD_REQUIRED`, never ready.

Only `/usr/local/sbin/log-platform-environment-identity-helper` may write the file. Promotion and rollback invoke it only as the argument vector `sudo -n /usr/local/sbin/log-platform-environment-identity-helper ...`: interactive password prompts, askpass/password piping, shell invocation, retry without `-n`, and fallback to broad root access are prohibited. Missing NOPASSWD authorization fails with the bounded `BLOCKED_BY_CANONICAL_IDENTITY_PRIVILEGE_PATH` classification. It runs Python in isolated mode and imports its hash-bound parser only from root-owned `/usr/local/lib/log-platform/environment_identity_file.py`, never from the user-writable checkout. Its sudo exposure is limited to that program, whose own allow-list hard-codes the path and value set. Update/restore require expected value, checksums and exact generated attestation. Provisioning backups are never siblings of repository files: they are restricted checksum-bound files in the external recovery root, with every recovery-specific directory exactly `0700`, every backup/evidence file exactly `0600`, owner/group resolved from the fixed `logplatform` service account, no symlink traversal, byte verification, and fsync before any source replacement. Dry-run and root execute validate the same UID/GID/mode contract; root EUID never changes the expected owner, and any present `SUDO_USER`/`SUDO_UID`/`SUDO_GID` tuple must exactly match that service account. The promotion plan binds the installed helper, source, parser dependency, consumers and reload actions. The unprivileged CLI journals the helper result and pauses at `runtime_reload_required` until separately approved restarts/recreation converge.

Pre-provisioning inspection uses a separate no-write boundary. Secret-bearing legacy environment files remain root-only; permissions are not broadened and the service user gets no general file-read primitive. Sudo permits only `/usr/local/sbin/log-platform-runtime-identity-inspector inspect-runtime-identity-sources` as root, with no wildcard arguments, environment preservation, shell, editor, path parameter, or alternate root. The self-contained installed script runs Python isolated mode, clears unsafe Python/loader variables, uses only its fixed three-file allow-list, rejects links/non-regular/oversized or changing files, performs no shell/network/subprocess/write operation, and reveals only identity-key state plus bounded metadata/checksums. Repository code and user site packages are never imported or executed by this privileged inspector.

Runtime provisioning and every promotion plan/execute/resume/rollback path also require a clean, resolved Git repository before plan or attestation generation and before any database, privileged-helper, or filesystem mutation. The shared guard uses porcelain-v2 machine output from the actual repository root and rejects staged, unstaged, deleted, untracked, conflicted, dirty-submodule, merge, rebase, cherry-pick, and revert state. Its failure output is bounded to repository identity, category counts, at most twenty relative paths, and operation state; it never includes diffs or file contents. Committed customer-facing changes are acceptable after normal review, but uncommitted changes are not. The tools never stash, reset, restore, discard, or auto-commit operator work.

New v5 promotion plans bind the exact clean original execution HEAD, and initial execute recomputes it before journal creation. Recovery-v2 retains its separately documented original/current implementation binding. Resume-v2 alone binds both the frozen original HEAD and a clean live implementation HEAD and accepts only identical-or-descendant ancestry with separately hashed resume assets. Any commit after a resume-v2 dry-run still invalidates that approval. The inspector bootstrap installer remains separate because it binds its exact HEAD and independently hashes every source immediately before writing its two fixed destinations.

Contract v5 makes the printed compact canonical plan itself the complete approval boundary: sorted keys, clients, implementation assets, historical entries and exclusions bind host/branch/HEAD, canonical metadata, database identities and least-privilege capabilities, live systemd and Docker provenance, Compose fingerprint, checkpoint/recovery assets, effective sudo policy, recovery history and later runtime gates. Execute reconstructs and byte-compares v5 before its first journal write. v3/v4 forward attestations are superseded; the v5 attestation binds host, HEAD, `contract=v5`, sorted client UUIDs and the full plan hash. Historical v4 remains readable for recovery-v2.

### Resume-v2 finalization boundary

`environment_identity_resume_plan_v2` is the only executable forward-finalization approval for an existing v5 `in_progress` journal. The executable attestation contract remains `resume-v2`, while the serialized plan schema is version 3. It binds the frozen original execution HEAD/assets as history and a clean identical-or-descendant resume implementation HEAD with its own live asset hashes. The dual-HEAD relaxation is confined to resume-v2; original v5 execution and recovery-v2 retain their own stricter contracts. Resume-v1 and hash `2b4fafc8d4b43446fe2d21a7da5d1ed57ff13f476fd70e8c9a8dbfc3174e67f5` are permanently diagnostic-only.

Plan schema 3 also binds an actual remote proof collected with `git ls-remote origin refs/heads/main`: normalized `origin` repository identity, the exact full ref, the actual remote SHA, the current local HEAD, and their equality. Cached `origin/main` is not evidence and the collector does not fetch or update it. An unreachable remote, absent or duplicate ref, malformed SHA, changed repository identity, unsupported branch relationship, or local/remote inequality fails closed. Remote movement is `RESUME_REMOTE_HEAD_DRIFT`, not journal drift. The actual remote is queried during dry-run collection, before lock acquisition, again under the lock before the first write, and at each later non-journal plan revalidation. Unavailability is never replaced with an approved or cached value; after a committed journal write it is a partial result requiring reconciliation.

The same plan binds `migration_054_complete_catalog_v1` from read-only PostgreSQL catalogs. This is an expected-contract check, not a hash of arbitrary observed state: it requires the immutable platform database identity/name, exactly one `054_environment_identity_resume_contract.sql` history row and that filename as the migration ceiling; both nullable, default-free text audit columns and their complete catalog metadata; both exact named, validated check predicates; the expected trigger function body hash `8fb25571bc049a60ba628e2c2bc3a2582d903a51c65734d1302946eef524cd8c`, identity, return type, owner, language, SECURITY mode, volatility and `proconfig`; and the enabled row-level BEFORE UPDATE trigger bound to that function with its normalized definition. This production-lineage contract treats column `attnum` 22/23 as a hard invariant because migration 054 is additive to the exact migration-053 journal layout; a restore that assigns different positions requires independent review and a regenerated contract. OIDs are excluded.

PostgreSQL catalog absence is validated in raw form before serialization, then represented explicitly in canonical plan bytes: `identity_kind=not_identity`, `generated_kind=not_generated`, `default_expression=no_default`, trigger-function `identity_arguments=no_arguments`, and `proconfig=not_configured`. These non-empty sentinels mean a specific expected absence; they are not defaults for missing evidence. An unknown raw value is schema drift, while a missing key, JSON null, or empty string remains rejected by the global fail-closed plan validator.

Both migration-054 column comments are blocking capability metadata: changing or removing either is `RESUME_SCHEMA_CONTRACT_DRIFT`. The contract's `target_promotion_resume_audit_state` binds the exact operator-selected promotion ID and requires that target row's `resume_contract` and `resume_plan_sha256` are both null. The parameterized catalog query is deliberately scoped to that UUID; completed or failed historical journals with write-once resume-v2 evidence are preserved and excluded from this gate, so they do not make resume-v2 single-use for the journal table. The same promotion ID must match the approval identity, journal binding and writable-row scope. A target value produces the truthful diagnostic `target promotion resume audit columns already contain values` with only the sanitized target ID. Any absent, partial, unvalidated, disabled, rebound, altered, history-incomplete, comment-drifted, target-ID-mismatched, or already-audited target shape is rejected before it can become approvable. The complete target-scoped schema contract is recollected during plan generation, pre-execution validation, under the advisory lock before the first write, after each progress write, and before atomic finalization. Target drift fails closed; unrelated audit-history changes do not alter this target contract.

All serialized plan shapes before version 3 are non-approvable; missing remote or schema sections receive no implicit defaults. The production plan with SHA-256 `4a409a35ae96cb64d4c6027af0c04db5f2dfe58a3e9dcb6436f58f073dfbb5f5` is explicitly rejected as an incomplete approval binding and must never be approved or executed. No plan generated before this fix is approvable.

The visible single-line attestation binds host, promotion ID, `contract=resume-v2`, both HEADs, original v5 plan hash, exact resume plan hash, journal state/current/remaining suffix, canonical identity hash, platform/client UUIDs, systemd PID and InvocationID, Docker container ID and Compose fingerprint, plus `UUIDS_UNCHANGED=true`, `NO_PERSISTENT_WRITES=true`, and `NO_RUNTIME_RESTART=true`. Approval uses exact byte/string comparison: no case folding, whitespace normalization, substring acceptance, or weaker-contract fallback.

Resume-v2's effective sudo boundary is `sudo_n_l_normalized_v2`: every subprocess collector uses locale `C` and removes `COLUMNS`; it parses the complete ordered command-policy section from `sudo -n -l`, including broad rules that match the helper invocation, run-as identity, tag transitions, command order, later matches, and the final effective password requirement. The primary fingerprint covers that complete normalized structural record set, not translated/wrapped presentation or a constant successful helper record. At least one exact root `NOPASSWD` helper-specific rule is required, and a later matching rule that makes the helper require a password fails closed. The frozen v5 fingerprint remains bound as historical evidence. Helper/parser source and installed hashes/metadata, provisioning checkpoint/recovery files, journal history, original assets, and live resume assets (including the imported recovery module and shared environment validator) are separate security bindings.

The command-policy parser is deliberately narrow and is not a general sudoers implementation. Command lists are split by an explicit tokenizer rather than a lookahead regex, so `ALL` is recognized anywhere in a list — `/bin/true, ALL`, `ALL, /bin/true` and `/bin/true,ALL` are all treated as matching the helper. It supports exactly `ALL`, absolute command paths, negated absolute paths, comma-separated lists of those forms, backslash-escaped commas inside a command specification, the already-supported run-as forms, and the `NOPASSWD`/`PASSWD` authorization tags. Everything else fails closed with `RESUME_SECURITY_BINDING_DRIFT` before plan construction: unexpanded or negated command aliases such as `LOGPLATFORM_HELPER`, any other bare uppercase identifier, malformed lists, empty tokens, a trailing or otherwise ambiguous escape, wildcard and argument forms outside the supported set, and any command specification that cannot be proven not to match the helper. Tags are equally strict — a rule that can match the helper may carry only `NOPASSWD` or `PASSWD`, so `SETENV`, `NOEXEC`, `EXEC`, `LOG_INPUT`, `LOG_OUTPUT` and unknown tags are rejected rather than merely fingerprinted. Unsupported syntax makes the plan unsupported; it never yields an approval-ready fingerprint. The fingerprint covers the ordered normalized records, so rule order, an added broad `ALL`, a tag change, a list change, a run-as change, a negation, or an encountered unsupported rule all change it.

Long-running health is proven independently: systemd `log-platform-api.service` uses `http://127.0.0.1:8001/docs`; the Compose `api` container uses `http://127.0.0.1:8000/docs`. False/unavailable health cannot enter an approval-ready plan. Systemd binds fragment/drop-ins, PID, InvocationID, active/sub-state, `NeedDaemonReload=false`, ControlGroup and current cgroup membership. Its enforced uniqueness rule is that the service cgroup contains exactly `MainPID`; the listener socket for `127.0.0.1:8001` must be owned by that PID. Every convergence component is derived from those observations, canonical source, process identity, health and manager metadata. Docker binds exactly one active API container, full ID, image reference/digest, ordered Compose files/working directory, configuration fingerprint, canonical source and observed identity, excluding volatile wholesale inspect/network/timestamp/PID data. Its convergence components are likewise derived rather than asserted: `running` from the observed state, `unique_active_api_container` and `duplicate_active_container` from the active container count, `identity_matches` from the observed identity against the target environment, and `canonical_source`/`health_passed` from the actual probe results. The plan refuses when any required component is false, so the serialized fields change whenever the underlying observations change.

#### Deliberately narrow systemd proof envelope

The resume-v2 systemd proof intentionally supports exactly one shape and claims no broader portability:

- exactly one persistent process in the `log-platform-api.service` cgroup, which must be `MainPID`;
- the cgroup v2 unified hierarchy;
- the currently supported loopback listener representation for `127.0.0.1:8001`, owned by that same PID;
- one uvicorn worker.

The following are **not** supported and fail closed rather than being approved on a best-effort reading: multiple uvicorn workers, because the cgroup would then hold more than `MainPID`; a native `::1`-only listener, because the collector does not represent it; cgroup v1 or a hybrid hierarchy, because the unified membership file is absent; and any unexpected helper, reload or leftover process still resident in the service cgroup. Widening any of these requires a separately designed and reviewed collector and proof, not a relaxation of the current guards.

The executable module has no persistent environment mutation primitive, helper invocation, business/job/provider/mail/backup/prune/snapshot/backfill import, or runtime restart/recreation action. `runtime_reload_required` and `runtime_processes_verified` are separately committed progress writes. Final verification is appended and the exact row is transitioned from `in_progress` to `completed` in one atomic transaction that also records the write-once resume contract/hash and clears the active failure/current-step fields. A fresh read-only connection must then observe the exact full step list and audit binding. All observations and both approval reconstructions use read-only connections; the write connection opens only after exact hash/canonical/attestation equality under the advisory lock.

Original forward-v5 finalization is now atomic on the same principle. `journal_finalize_forward_v5` appends `final_verification` and transitions the exact row to `completed` in one explicit transaction, requiring `state='in_progress'`, `current_step='final_verification'`, the exact ordered completed-step prefix ending with `runtime_processes_verified`, and exactly one affected row; zero, multiple or unexpected rows roll back. It deliberately does not touch the migration-054 resume audit columns, so it remains valid for journals created under migration 053. The retired split of a committed `final_verification` step followed by a separate completion transition is gone, so no interruption in either executor can leave the unrecoverable shape of every step complete with `current_step=NULL` and `state='in_progress'`.

The whole forward-v5 path — not only that one helper — is schema-053 compatible. Journal inspection reads the optional migration-054 audit fields through `to_jsonb(journal) ->> '<column>'`, which is null when the row type has no such field, so no forward read can raise a missing-column error against a journal created before the migration; missing-column errors are never caught and discarded, no identifier is interpolated from operator input, and no audit value is fabricated. A separate read-only, per-connection and deliberately uncached catalog probe of exactly `ops_control.environment_identity_promotion` reports which audit columns exist. Forward and rollback execution require only a *consistent* schema and perform this check through a short-lived read-only probe before opening any write-capable execution connection, before attempting the advisory lock, and before invoking mutation helpers. Resume-v2 additionally requires both columns and refuses with `RESUME_V2_AUDIT_SCHEMA_REQUIRED` and `writes_performed=false` before its advisory lock and before any write connection opens. A half-applied migration — exactly one audit column — blocks all executors with `ENVIRONMENT_IDENTITY_RESUME_AUDIT_SCHEMA_INCOMPLETE` before any mutation, and is never treated as either schema version.

The forward executor's interruption reporting matches resume-v2's. An unexpected non-`PromotionError` inside its execution boundary is converted into a structured `FORWARD_V5_EXECUTION_INTERRUPTED` result that preserves the original exception class, carries a secret-redacted message and the current step, and reports `writes_performed=true`, `reconciliation_required=true` and the partial exit code whenever the first journal write has already committed. A durable client-marker, control-plane, platform-marker, canonical-file or progress write can therefore never be reported to the operator as a plain precondition failure. A forward session owns the write, read-only and lock connections plus lock-acquired state. Cleanup independently closes the write connection, closes the read connection, releases the advisory lock, and closes the lock connection; every phase has its own exception boundary and sanitized structured evidence.

Interruption reporting after a durable write is truthful for every exception type, not only for the platform's own `PromotionError`. Once any journal transaction commits, the executor tracks that locally and every subsequent failure reports `writes_performed=true`, `reconciliation_required=true`, exit code `EXIT_PARTIAL`, and a structured result; an inner exception detail claiming `writes_performed=false` can never override that local durable-write state. A raw exception — `psycopg.OperationalError`, `RuntimeError`, a connection-close failure, a fresh-read failure — is wrapped as `RESUME_V2_EXECUTION_INTERRUPTED` or `FORWARD_V5_EXECUTION_INTERRUPTED` carrying the original exception class, a sanitized message, the current execution phase, whether finalization may already have committed where applicable, and whether read-only reconciliation is required. Credentials, DSNs and secret assignments are redacted from that message. Before the first committed write an unexpected exception reports `writes_performed=false` with the precondition exit code. Primary execution errors always take precedence: cleanup failures are secondary ordered `cleanup_failures` evidence and cannot change the primary classification. A cleanup-only failure is reported as `RESUME_V2_CLEANUP_FAILED` or `FORWARD_V5_CLEANUP_FAILED`; after any durable write it is a partial, ambiguous result with `reconciliation_required=true`, even when the journal may already be completed. The operator must reconcile with the valid read-only form `--inspect-promotions all --promotion-id '<PROMOTION_UUID>'`. Cleanup is not claimed to be infallible; the guarantee is that a cleanup failure cannot hide durable execution state or replace the primary classification.

Client marker writes use `ops_control.promote_environment_identity_v1` from client migration 045. It is SECURITY DEFINER with fixed `pg_catalog, ops_control` search path, caller-independent identifiers, primary-row lock, database/role/UUID/source checks and a one-column update. `PUBLIC` has no EXECUTE; only the intended runtime role receives EXECUTE and direct table UPDATE is revoked. Execute mode fails closed if the exact signature/version is missing or if the runtime role still has direct marker UPDATE. UUID, client code/id, database name and every other marker column are immutable under this path.

Promotion and rollback client completion means **committed and independently verified**, never merely visible in the mutation session. Preflight uses separate read-only connections. Each migration-045 call starts from an `IDLE` connection and owns one top-level transaction; successful context exit commits, commit errors propagate, and the mutation connection is closed. A new explicitly read-only connection must then observe the target marker, UUID and least-privilege capability before the platform journal may append the client step. In-session success inside a nested savepoint is not durable evidence.

The session-level advisory lock is held by a dedicated autocommit connection and performs no application commit. Resume and recovery-v2 rollback lock connections set the session default `default_transaction_read_only=on`, verify it with `SHOW default_transaction_read_only`, and fail closed unless it is `on`; advisory lock/unlock remain allowed, while ordinary writes are rejected by PostgreSQL. The lock connection is never reused for rollback writes. No general write-capable resume connection opens before hash and attestation revalidation under that lock. Platform marker/control-plane changes and every journal transition use explicit transactions. Unlock cannot commit unrelated work, and unlock or commit failures are bounded errors rather than suppressed cleanup. Resume builds a current-state reconciliation plan: actual fresh-connection state is authoritative over historical `completed_steps`, and unsupported divergence stops before writes.

Resume-v2 is only the post-convergence finalization contract. An `in_progress` journal whose remaining frozen-plan suffix begins before `runtime_reload_required` is classified `PRE_RUNTIME_FORWARD_RESUME_CONTRACT_REQUIRED` before resume-v2 approval validation; it requires a separately designed and reviewed forward-recovery contract. Atomic finalization on both execution paths removes the finalization dead-end but does not change this earlier-stage limitation, and no broad early-stage recovery contract is implied. Resume-v1 is not restored.

Failed-promotion rollback uses `failed_environment_identity_recovery_plan_v2` and exact `contract=recovery-v2` attestation. It binds the current failed journal, actual database/canonical/runtime state, helper policy/assets, checkpoint/recovery artifacts, implementation HEAD and exclusions. Audit-only recovery-v1 hash `9d417d3bb88451d1edb1bba4c67564ae0b3947a59cec93060bd25f7ad6278cf5` is permanently non-executable. When canonical identity already equals the rollback target and the journal has no promotion backup, the hashed plan contains explicit `null` backup/evidence fields and excludes helper invocation. Successful rollback requires fresh cross-surface/readiness verification, a separately committed and re-read journal finalization, and atomic checksum-bound evidence before success output.

Rollback execution owns its write connection, read-only autocommit advisory-lock connection and lock-acquired state in one release-once session. Cleanup order is deterministic: close the rollback write connection, release the advisory lock only if acquired, then close the lock connection. Every operation has an independent exception boundary, so one cleanup failure cannot skip the others. Forward-v5, resume-v2 and rollback cleanup evidence uses the same sanitized record shape: `operation`, `exception_class`, `detail`.

The primary rollback error always takes precedence over cleanup. A `PromotionError` retains its classification and message; cleanup failures are ordered secondary evidence and can only upgrade the exit to partial after a rollback mutation started. A raw pre-mutation exception becomes `RECOVERY_V2_EXECUTION_INTERRUPTED` with `writes_performed=false`. A raw exception after a client/platform/journal/evidence mutation starts becomes `FAILED_PROMOTION_RECOVERY_PARTIAL_STATE` with the original exception class, sanitized detail, phase, completed and in-flight actions, commit-ambiguity flags, `writes_performed=true`, and mandatory read-only reconciliation. If rollback reaches its normal durable result but cleanup fails, `RECOVERY_V2_CLEANUP_FAILED` reports the observed journal/evidence state as ambiguous partial success; it never regresses `rolled_back` to `failed`. Cleanup remains fallible, but it cannot hide durable recovery state, discard known evidence, or replace the primary recovery classification.

Production can enforce stricter operation-specific guards after promotion. The common guard requires runtime/platform/client equality; guarded production writes may also require a clean worktree, explicit client scope, dry-run restrictions, and an operation-specific production confirmation. The promotion attestation does not replace those later confirmations. Missing identity guards on a component are surfaced as `unguarded` by readiness inspection rather than being represented as verified.

Do not edit runtime identity declarations, marker rows, or control-plane expectations manually. Use dry-run, preserve the immutable output and checkpoint, execute only after explicit approval, and inspect the journal after any interruption. Do not put an attestation in runner params, logs, or a secret store; it is non-secret command intent, but its exact plan binding must remain auditable.

Provisioning success is a verified postcondition, not merely a completed write. Canonical contents and metadata, removed legacy assignments, installed hashes and ownership, effective systemd merge order, external recovery evidence, and a clean Git worktree are checked after writes. Failure after any write returns bounded `RUNTIME_IDENTITY_PROVISIONING_FAILED_PARTIAL_STATE` evidence with completed step names and rollback references but no secret contents. Recovery validation failures report only the failing path, phase, expected/actual UID/GID/mode, and real/effective UID. A permissive but otherwise valid recovery root is repaired only by the separate attested `remediate_runtime_identity_recovery_permissions.py` plan; it must never be folded into provisioning or systemd remediation approval.
